## Context

ChangePilot 的可靠工作流与规划 Agent 需要通过真实工具调用证明其安全属性。直接连接企业环境既不可行也不适合开源项目，因此需要一个行为足够真实、状态可观察、可以随时重置的本地变更沙箱。当前开发环境是 Windows，后续可能迁移到 WSL2；Docker 尚未安装，DeepSeek API 额度有限，因此执行沙箱必须与容器和在线模型解耦。

演示对象是一个订单服务：V1 使用初始订单表和接口契约，V2 引入新的订单字段及对应服务行为。升级需要先检查环境、迁移 Schema、切换服务版本、执行健康检查与业务冒烟测试；任一步骤失败时，工作流按照策略停止或执行补偿。

## Goals / Non-Goals

**Goals:**

- 提供无需 Docker 即可运行、可重置且跨 Windows/WSL2 的本地沙箱。
- 让数据库迁移、部署、验证和回滚都通过统一的受控工具接口执行。
- 稳定复现升级成功、验证失败回滚和进程中断后恢复三种核心演示。
- 保留 PostgreSQL 或容器化实现的替换边界，使 V1 的测试资产可以复用。

**Non-Goals:**

- 不连接或模拟完整的生产基础设施、Kubernetes、云平台或 CI/CD 平台。
- 不允许执行任意 Shell、任意 SQL 或访问沙箱目录之外的资源。
- 不在 V1 中要求 Docker、PostgreSQL 或多服务分布式部署。
- 不把示例订单服务建设为业务完整的电商系统。

## Decisions

### 1. V1 采用进程内订单服务与 SQLite

订单服务以可调用的应用组件暴露健康检查和业务接口，数据库使用独立 SQLite 文件。每次演示创建隔离的运行目录，避免端口、后台进程和容器状态导致不稳定。

选择该方案是因为它能在 Windows 与 WSL2 上提供一致的零依赖体验，并保留真实的持久化、事务和 Schema 版本行为。直接以 Docker Compose + PostgreSQL 起步更接近部署现场，但会把环境安装问题变成项目的主要风险；纯内存 Mock 则无法体现数据库变更经验。

### 2. 通过版本化工具契约隔离执行环境

每个工具声明名称、输入 Schema、输出 Schema、风险级别、超时、幂等键规则和补偿能力。工作流运行时只能从注册表调用工具，不能让模型拼接并执行任意命令。工具结果使用统一状态模型，并携带变更前后版本和可审计摘要。

这样既能让 SQLite 实现与未来 PostgreSQL 实现共享行为测试，也能把 Agent 的非确定性限制在“提出计划”而不是“直接操作环境”。允许模型生成 Shell/SQL 更灵活，但无法可靠实施审批、重试和幂等保护。

### 3. Schema 迁移使用账本与显式前置条件

沙箱维护独立的迁移账本。迁移工具在执行前检查当前 Schema 版本、目标版本和数据库指纹；重复调用相同迁移时返回已完成而不重复修改。V1 到 V2 的迁移采用向后兼容的演进步骤，并提供仅在满足安全前置条件时可用的逆向迁移。

默认补偿优先回退服务版本；是否逆向迁移数据库由计划中的补偿策略和运行时安全检查共同决定。这比无条件回滚 DDL 更接近企业实践，也可以展示“业务回滚”和“数据回滚”并非同一件事。

### 4. 故障注入绑定到命名步骤边界

故障配置使用场景文件指定工具名、调用序号和故障类型，例如健康检查失败、工具超时或进程中断。故障注入器不修改业务逻辑，重置沙箱后相同配置产生相同结果。

命名步骤边界便于端到端测试断言和面试现场演示。随机故障更像混沌测试，但会降低可复现性，因此不作为 V1 默认行为。

### 5. 沙箱状态与工作流状态分离

沙箱目录保存服务版本、数据库和迁移账本；工作流状态库保存步骤、审批、检查点与审计事件。恢复时，运行时先读取工作流检查点，再通过环境检查工具核对真实沙箱状态，只有二者一致或可安全收敛时才继续。

这一设计主动覆盖“记录显示已执行，但进程在写入结果前中断”等边界情况，避免仅依赖工作流数据库做出错误判断。

## Risks / Trade-offs

- [SQLite 与 PostgreSQL 的 DDL/并发语义不同] → 将数据库操作封装在适配器中，用契约测试固定共同语义，并把 PostgreSQL 作为后续增强。
- [进程内服务弱化了真实发布系统的复杂度] → 保留部署工具接口和版本切换状态机，后续可替换为容器或外部部署适配器。
- [逆向迁移可能造成数据损失] → 迁移必须声明可逆性和前置条件；不满足条件时只回退服务并进入人工处理状态。
- [故障注入路径污染正常逻辑] → 故障注入仅通过测试配置和工具边界启用，默认关闭并记录审计事件。
- [沙箱文件被越界访问] → 所有路径在解析后必须位于本次运行目录，工具不接受任意绝对路径。

## Migration Plan

1. 先实现 V1/V2 Fixture、重置能力和环境检查工具。
2. 增加迁移、部署、验证和补偿工具，并通过独立契约测试。
3. 接入可靠工作流运行时，完成无故障升级场景。
4. 增加健康检查失败和进程中断场景，验证回滚与恢复。
5. 后续在不改变工具契约的前提下增加可选 PostgreSQL/Docker 适配器。

## Open Questions

- V1 实施阶段需根据所选 Python Web 框架确定订单服务采用进程内测试客户端还是本地 HTTP 进程；两者必须共享相同业务接口契约。
- PostgreSQL 适配器是否纳入首个可演示版本，由 WSL2/Docker 环境准备情况决定，不影响本 change 的完成标准。
