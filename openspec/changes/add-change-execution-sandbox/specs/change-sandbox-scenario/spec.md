## ADDED Requirements

### Requirement: 可重置的订单服务基线
系统 SHALL 能够创建或重置一个隔离的订单服务 V1 沙箱，包含固定的示例数据、Schema 版本、服务版本和迁移账本。

#### Scenario: 创建干净的 V1 沙箱
- **WHEN** 用户创建新的演示运行或请求重置现有沙箱
- **THEN** 系统生成已知的 V1 状态，并且其环境指纹与基线 Fixture 一致

#### Scenario: 运行相互隔离
- **WHEN** 两个演示运行同时创建各自沙箱
- **THEN** 任一运行的数据库、服务版本和故障配置均不影响另一运行

### Requirement: V1 到 V2 成功升级场景
系统 SHALL 提供一个固定场景，通过环境检查、审批后的迁移、服务切换、健康检查和业务冒烟测试将订单服务从 V1 升级到 V2。

#### Scenario: 完成无故障升级
- **WHEN** 用户批准高风险步骤且所有工具正常返回
- **THEN** 工作流成功结束，服务和 Schema 均处于 V2，并保留每一步的验证证据

### Requirement: 验证失败后的补偿场景
系统 SHALL 支持在 V2 部署后的健康检查步骤注入确定性失败，并由工作流按照补偿策略逆序处理已完成动作。

#### Scenario: 健康检查失败触发回滚
- **WHEN** V2 部署完成但健康检查返回注入的失败
- **THEN** 工作流停止后续步骤、执行允许的补偿、恢复可服务状态并将运行标记为已补偿失败

#### Scenario: 数据库不满足安全回滚条件
- **WHEN** 健康检查失败且逆向迁移的安全前置条件不满足
- **THEN** 系统回退兼容的服务版本、保留数据库状态，并将运行置为等待人工处理

### Requirement: 进程中断后的恢复场景
系统 SHALL 支持在指定工具边界模拟执行进程中断，并在新进程启动后依据工作流检查点和真实环境状态恢复。

#### Scenario: 已提交迁移但未记录结果时中断
- **WHEN** 迁移已经提交但运行时在持久化步骤成功结果前中断
- **THEN** 恢复流程通过环境检查和幂等键识别迁移已完成，不重复修改数据库并继续后续步骤

#### Scenario: 工具产生副作用前中断
- **WHEN** 运行时在工具产生副作用前中断
- **THEN** 恢复流程安全地重新执行该步骤，并保持一次有效副作用

### Requirement: 可复现故障注入
系统 SHALL 允许场景按工具名称、调用序号和故障类型配置故障，并 MUST 在相同基线与配置下产生相同结果。

#### Scenario: 重放健康检查故障
- **WHEN** 用户重置沙箱并再次运行相同的健康检查失败场景
- **THEN** 故障发生在相同步骤边界，最终状态和关键审计事件与前次运行一致

### Requirement: 场景执行不依赖在线模型
核心沙箱场景 MUST 能够使用固定结构化计划或 Mock LLM 完整运行，不得要求 DeepSeek API、Docker 或外部数据库可用。

#### Scenario: 完全离线运行演示
- **WHEN** 环境没有模型 API 凭据、Docker 和 PostgreSQL
- **THEN** 用户仍可运行成功升级、失败回滚和中断恢复三个核心场景
