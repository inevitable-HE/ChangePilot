## Context

前三个 change 分别提供可靠工作流、知识增强规划 Agent 和本地变更沙箱，但这些能力需要一个面向操作者的入口，以及一套可重复的质量证据。企业研发变更通常包含请求提交、计划评审、人工审批、执行监控、失败处置和事后审计；只提供命令行会弱化项目的产品完整度，也难以在面试中快速传达安全设计。

同时，LLM 的输出质量无法仅靠单元测试或一次演示判断。评测必须区分确定性工程能力与模型能力，并保证默认运行不消耗 DeepSeek 额度。

## Goals / Non-Goals

**Goals:**

- 提供安静、信息密集、适合研发变更操作的本地 Web 控制台。
- 让计划证据、风险、审批点、步骤状态、补偿和审计事件可被清晰检查。
- 建立版本化、可离线重放的评测集和机器可比较的指标报告。
- 对可选在线评测施加调用次数与费用上限。

**Non-Goals:**

- 不制作营销落地页、通用低代码工作流编辑器或聊天机器人外壳。
- 不在 V1 中实现多租户、企业 SSO、组织权限模型或移动端应用。
- 不用主观 LLM-as-a-judge 作为安全策略和工作流正确性的唯一判据。
- 不追求大规模并发压测或生产级可观测平台集成。

## Decisions

### 1. 使用 FastAPI API 与 React 运营控制台

后端提供变更请求、计划、审批、运行、审计和评测的资源型 API；前端使用 React 构建单页运营界面。Python 后端便于复用 Agent、评测和沙箱模块，React 适合表达步骤图、时间线、筛选和审批交互。

服务端渲染模板依赖更少，但随着计划审阅和实时状态增加会产生较重的页面状态管理；纯命令行则不满足快速理解项目全貌的目标。实施时优先复用仓库已有依赖，若尚无前端基础则采用最小 Vite 工程。

### 2. 首屏是运行工作台而非介绍页

控制台采用紧凑的三段式信息架构：运行列表与状态筛选、当前运行的计划/步骤主视图、证据与审计详情。创建变更请求是主操作；风险、等待审批、失败和补偿状态使用不只依赖颜色的明确标识。

审批动作显示目标步骤、风险级别、输入摘要、知识证据和补偿策略。界面不允许直接编辑已持久化的执行状态，也不提供任意工具调用入口。

### 3. 使用带游标的服务端事件流

后端为每个运行提供按单调序号排序的事件流。前端首次读取状态快照，再通过 Server-Sent Events 接收增量；断线重连时携带最后事件序号补齐缺失事件。所有状态以服务端查询结果为准。

SSE 满足单向状态更新且实现成本低于 WebSocket。轮询可以作为降级方案，但不是默认实时机制。

### 4. 审计报告由后端基于持久化事件生成

导出报告包含请求、计划版本、引用、审批、工具输入摘要、步骤结果、补偿、模型用量和最终状态。前端不能提交自定义审计内容，报告中的敏感字段由后端统一脱敏。

V1 使用可读的 Markdown/JSON 报告便于面试讲解与自动校验；PDF 可作为后续增强，不增加首版文档渲染依赖。

### 5. 评测分为确定性套件与可选在线套件

确定性套件使用固定计划或 Mock LLM，验证计划 Schema、安全规则、审批阻断、工具幂等、故障恢复和补偿。模型套件使用版本化输入与知识库快照，评估信息澄清、引用完整性、计划有效性和风险识别；默认同样使用 Mock 响应，DeepSeek 仅在显式启用时运行少量样例。

安全与工作流指标通过规则和最终状态计算，不交给另一个 LLM 判断。需要语义判断的规划质量采用明确的期望事实、允许集合和引用匹配，避免评测本身不稳定。

### 6. 指标按版本保存并支持基线比较

每次评测记录代码版本标识、数据集版本、提示版本、模型配置、知识库版本、随机种子、逐样例结果和聚合指标。核心指标包括计划 Schema 通过率、引用完整率、危险动作阻断率、恢复成功率、补偿成功率、端到端完成率、延迟、调用次数和估算成本。

基线阈值由评测配置声明。若安全类指标低于阈值或成本超过上限，评测命令返回失败；界面只展示结果，不改变判定。

## Risks / Trade-offs

- [前后端同时开发扩大首版范围] → 控制台限定为单用户核心路径，先完成 API 契约和关键页面，不建设通用设计系统。
- [SSE 在开发代理或断线时丢事件] → 每条事件持久化并带序号，客户端用快照和游标恢复。
- [固定评测集被提示词过拟合] → 划分可见开发集与保留回归集，并覆盖多种失败类型和同义表达。
- [模型评测结果存在波动] → 默认使用确定性参数、固定版本和容差区间，安全指标始终由规则判定。
- [在线评测耗尽低额度 API] → 默认禁用，启用前估算上限，并在达到调用或费用阈值时硬停止。
- [审计报告泄露密钥或原始敏感内容] → 在持久化和导出边界统一脱敏，模型凭据永不进入事件载荷。

## Migration Plan

1. 先定义只读查询、命令提交和事件流 API，使用固定数据验证契约。
2. 实现运行列表、计划审阅、审批与执行监控的核心控制台。
3. 接入真实工作流、Agent 和沙箱状态，并增加断线恢复测试。
4. 实现离线评测运行器、固定数据集、指标计算和基线比较。
5. 增加控制台评测结果页及 Markdown/JSON 审计报告导出。
6. 最后增加受预算保护的 DeepSeek 可选评测入口。

## Open Questions

- 实施阶段根据工作流存储接口决定评测结果复用同一 SQLite 数据库还是使用独立结果文件；无论选择哪种方式，都必须保持版本化导出格式。
- 首版步骤依赖图可采用简化 DAG 列表或图形库，选择以可读性、无布局重叠和测试稳定性为准。
